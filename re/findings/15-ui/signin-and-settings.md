# Sign-in, session lifecycle, and gating semantics (VictoryShield.exe + UWPApp.SignInControl)

Scope: the sign-in/switch-users/confirm-password flow (`UWPApp.SignInControl` hosted by `CSignInDialog`), how credentials move UI→backend→local store, `WTSRegisterSessionNotification` session lifecycle, the tray "Logout … disables web access" gating chain, the "Filter guardian"/"technical issues with the filter" flow, and the settings division between `VictoryShield.exe` and `vs-config.exe`. Companion: `ui-architecture.md` (windowing/XAML/IPC/D3D capture). Cross-refs: `re/findings/02-artifacts/local-db.md` (ce-file `logins`/`switch_users` schema), `logs.md` (QUIT/USER_SETTINGS_CHANGE/USER_LOGOUT vocabulary), `14-watchdog/watchdog.md` (restart chain).

## What it does

Sign-in is a password-based CE-account login (not OS login): the user picks/types a CE username, enters a password in the XAML `passwordInput` box, and the host authenticates against CE's backend with HTTP Basic-style credentials (`CE_BASIC`), caches the result in the local `ce-file` `logins` table, and publishes "who is signed in / which services are on" into the shared `CE_SPYMapObj` block that the filtering components consult. "Switch user" swaps the signed-in CE account (state `SWITCHING_USER`, DB table `switch_users`); a "confirm your password" mode re-uses the same control. Session lock/logoff/unlock events gate screen capture and force-logout checks. Signing out ("Logout of the Victory Shield service -- disables web access") sends `USER_LOGOUT` to the comm service and warns "Signing out will disconnect you from the Internet." — web access is then blocked by the DNS/URL filtering components while no user is signed in.

### 2. What `CryptographicBuffer` is actually used for (correcting the baseline)

The baseline tagged `Windows.Security.Cryptography.CryptographicBuffer` (`0x180041860`) as "[INFERENCE: used for sign-in token/nonce handling]". **Evidence says otherwise**: the only consumers are `FUN_1800020e0` (`ICryptographicBufferStatics` vtable+0x68 = `DecodeFromHexString`) and `FUN_180001f20` (vtable+0x50 = `CopyToByteArray`) (both decompiled), and both are called **only** from the coroutine `FUN_18001a170` (decompiled), which then builds `Windows.Storage.Streams.InMemoryRandomAccessStream` + `DataWriter` (`WriteBytes` vtable+0x60), and awaits `BitmapImage.SetSourceAsync` (`Windows.UI.Xaml.Media.Imaging.h` line refs in the record) — i.e. **hex→bytes→stream→BitmapImage image decoding**, not credential handling. No token/credential crypto exists in `UWPApp.dll`; the DLL has no network imports at all (baseline: 83 imports, all WinRT/UCRT plumbing).

## Linux-reimplementation notes

- Auth: OIDC/browser or password-POST to the daemon; cache the session in the local DB (LustLess `logins` equivalent) keyed by OS user; "confirm password" re-auth before sensitive settings changes is a good UX pattern to keep.
- Do not copy the credential path shape of CE: the UI hands the plaintext password to the host process which stores derived credentials in a local SQLite DB and publishes identity via shared memory. On Linux prefer: daemon holds the session token (mode-0600 store), UI never sees long-lived secrets; scope the filter state to the daemon.
- Gating: "signed out ⇒ web blocked" should be a single policy flag owned by the enforcement daemon; UI events (`USER_LOGOUT`/`USER_SETTINGS_CHANGE`) are just notifications. CE's DNS-filter approach (DoH resolver such as CleanBrowsing adult-filter) is directly portable — a local resolver/proxy honoring per-user policy.
- Session events: logind `Lock`/`Unlock`/`SessionNew`/`SessionRemoved` D-Bus signals replace `WTSRegisterSessionNotification`; same gating rule (capture only while unlocked and display on).
- Filter-health + break-glass: CE's `covenanteyesfilter.com/healthcheck` probe plus a "filter guardian" override is a safety valve against a broken filter locking out the household; an ethical LustLess should keep a local (not remote) health probe and an audited local override, never silent unfiltered bypass.
