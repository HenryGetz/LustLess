# UI architecture — VictoryShield.exe + UWPApp.dll (windowing, XAML Islands, web content, UI↔service channel, D3D11/DXGI verdict)

Scope: `VictoryShield.exe` (27,191 fn, image base `0x140000000`) and `UWPApp.dll` (829 fn, image base `0x180000000`), plus the XAML blobs `C:\Program Files\CE\SignInControl.xbf` (15,534 B) and `App.xbf` (548 B). Complements `re/findings/00-baseline/VictoryShield.exe.md` and `UWPApp.dll.md` (metadata/imports there; behavior here). Cross-refs: `re/findings/02-artifacts/logs.md` (comm-service log vocabulary), `re/findings/02-artifacts/local-db.md` (ce-file schema), `re/findings/01-dynamic-recon/live-surface.md` (no kernel/WFP enforcement). Updater/BugSplat internals are out of scope (another pass).

## What it does

`VictoryShield.exe` is a **Win32/MFC tray application** (single main window that lives in the notification area, plus modal dialogs). It is the "face + policy state machine" of the client: sign-in/sign-out UI (a XAML Island hosting `UWPApp.SignInControl`), tray menu, screen-capture scheduler for Screen Accountability (see the D3D11/DXGI verdict below), and the arbiter of web-access gating state. It does **not** embed a browser — all web surfaces open in the user's default browser via `ShellExecuteW`, two of them pointing at the local comm service (`http://localhost:48867`) or the CE website. The UI↔service channel is **Boost.Interprocess message queues** (`ce_user_event_message_queue` out, `ce_service_event_message_queue` in) with a small integer-coded message vocabulary, plus a legacy "SPY" shared-memory block (`CE_SPYMapObj`) through which other CE components learn who is signed in and whether filtering is active.

**D3D11/DXGI verdict (explicit): the D3D11/DXGI initialization in `VictoryShield.exe` is SCREEN CAPTURE (Desktop Duplication / `IDXGIOutputDuplication`), not rendering.** It is a statically-linked copy of CE's `ScreenCaptureLibrary` (`…\ScreenCaptureLibrary\src\WindowsScreenImageCapture.cpp`), namespace `ce::screencapture::WindowsScreen` / `Win32DxgiCapture`, used to grab per-monitor frames for Screen Accountability screenstates. There is no swapchain/composition/XAML-rendering use of D3D in the binary; the UI renders with MFC/GDI(+), and the XAML island is rendered by the OS XAML stack. See "D3D11/DXGI init — verdict: screen capture" below for the full chain.

## Linux-reimplementation notes

- Tray-first single-instance app: one hidden controller window + status icon; no browser embedding — open URLs in the user's browser (or a tiny local web UI served by the daemon, like CE's `localhost:48867` dashboard).
- UI↔daemon channel in LustLess should be a simple local socket or Unix message queue with an integer-coded vocabulary like CE's (`USER_SETTINGS_CHANGE`, `USER_LOGOUT`, `SEND_TELEMETRY`, `SEND_METRICS`, `COLLECT_DEBUG_LOGS`, `SET_WINDOWS_REGISTRY`, `QUIT`) — CE's queue names (`ce_user_event_message_queue`/`ce_service_event_message_queue`) are a good naming model.
- The `CE_SPYMapObj` block is a shared "policy state" cache (who is signed in, which services are enabled, install dir) with per-request reply slots (`ceFilterCheckReply%d`) — a LustLess equivalent is a small shared state file/socket broadcast; the32-slot reply table is over-engineering and can collapse to request/response IDs.
- Screen capture: `pipewire`/`xdg-desktop-portal` screencast (Wayland) or X11 `XShmGetImage`; CE's pipeline (per-monitor capture → WIC encode → screenstate JSON+images → classifier scoring) maps directly to (capture → encode → record). CE's DX9 fallback, HDR tone-mapping and DPI-awareness requirements have portal equivalents (`Format`, `size` hints); preserve the "skip capture when session locked/screensaver active" gating (`PdlEdi::setSessionOn`/`setDisplayOn`).
